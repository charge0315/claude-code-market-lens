【ALPHA FORGE 開発秘話 #04】寄り付きに間に合わない！ 23分半かかった朝の銘柄抽出

【ハッシュタグ】

締め切りが「相場の開始時刻」で決まっているバッチを、書いたことはありますか。
ALPHA FORGE の朝いちばんの仕事は、寄り付き前に銘柄を抽出しておくことです。東証が開く9時は、どれだけ頼んでも1秒も延びてくれません。
日本株のAI銘柄スクリーニング＆継続学習端末「ALPHA FORGE（アルファフォージ）」を、個人で設計・開発・運用しています。今回は、この「9時の壁」に3回ぶつかって、3回とも同じやり方で乗り越えた話です。

■ 今回の3行まとめ
1. 8時50分に始めていた朝の銘柄抽出は、実測で23分半かかり、寄り付きに間に合っていなかった
2. 処理を速くする前に「早く始める」ことで解決し、開始時刻を 08:50 → 07:40 → 07:30 → 07:00 と3回前倒しした
3. 3回目は9月25日。公開済みの記事と台帳の食い違いがきっかけで、「記事を書く前に定期実行を終える」順番に直した

――――――――――――――――――――――――――――――――

🚨 「市場が開くのに間に合わないね」

9月16日の朝、画面を見ていた私がAI（Claude Code）に投げたのは、この一言でした。
「ピックに時間がかかっていて、市場がひらくのに間に合わないね」

ALPHA FORGE では、毎朝決まった時刻に、中長期と短期の2つの抽出バッチが自動で動きます。当時の開始時刻は8時50分。寄り付きの10分前です。
AIに調べてもらうと、中長期の抽出だけで実測23分半かかっていました。9時13分過ぎまで終わらない計算です。

しかも、このアプリの裏方（Celery という定期実行のしくみ）は、Windows では「1件ずつ順番に処理する」モードでしか安定して動きません。中長期が終わるまで、短期の抽出は順番待ちになります。

気づいたのは、朝の画面を毎日見ている人間でした。テストはすべて通っていて、エラーも出ていない。ただ「相場の時計」で見ると遅すぎる。この感覚は、コードの中にはありません。
原因を数字で突き止めたのはAIです。どの処理にどれだけ時間がかかったかを実測して、「23分半」という根拠を出してくれました。

――――――――――――――――――――――――――――――――

⏱️ 速くする前に、早く始める

遅いなら速くすればいい、と考えるのが普通です。処理を並列にする、待ち時間を削る、キャッシュを効かせる。どれもエンジニアとしてはやりたくなる改善です。
ただ、それをやると変更は大きくなり、朝のバッチを壊すリスクも増えます。そもそも「間に合わせる」だけなら、もっと簡単な方法があります。始める時刻を早めることです。

AIは実測をもとに、安全のための余裕を見た開始時刻を提案し、私が採用しました。

［画像挿入位置：開始時刻の変遷図／ images/01_schedule_timeline.png ／キャプション：朝の銘柄抽出バッチの開始時刻の変遷（バーの長さは9/16の実測23分半を当てはめた目安）］

変遷を順番に並べると、こうなります。
1. 〜9月16日：8時50分開始。実測23分半で、寄り付きに間に合わない
2. 9月17日：7時40分開始（短期は7時42分）へ前倒し
3. 同じ9月17日：7時30分へ、さらに前倒し。8時5分に動く「note下書きの自動生成」が、抽出結果を材料に使うようになったため
4. 9月25日：7時00分へ前倒し（理由は次の章で）

性能改善をやらないわけではありません。ただ、「間に合わない」という今日の問題は、今日中に安全に直せるやり方で先に止める。速くするのは、そのあとで落ち着いてやればいい。この順番を決めたのは人間で、実測と時刻の案を出したのはAIでした。

――――――――――――――――――――――――――――――――

📰 3回目の前倒しは、朝の記事がきっかけだった

そして3回目は、まさにこの記事を書いている9月25日の朝に起きました。

1. 6時52分、抽出を手動で実行した。中長期は候補がすべて見送られ、0件だった
2. その結果をもとに朝の記事を書き、公開した
3. 7時30分、いつもの定期実行が動いた。「今日の中長期はまだ1件も採用されていない」と判断して、中長期の抽出をやり直した
4. その結果、1回目はAIの自信度38%で見送られていた銘柄が、2回目は40%で採用ラインをちょうど越えた

公開済みの記事には「中長期は0件」と書いてあるのに、台帳には1件ある。記事と台帳が食い違ってしまいました。
記事には追記で事情を書き足して対処し、そのうえで私が決めたのは「記事を書く前に、定期実行を終わらせておく」ことです。開始時刻を7時00分（短期は7時02分）へ前倒ししました。

ただし、この前倒しには副作用がありました。抽出の材料に使う「朝のトレンド情報の同期」は7時13分に動いていたので、抽出を7時に早めると、その日の朝の情報が間に合わなくなります。
そこで私の判断で、朝の分だけ同期を6時45分に切り出しました（同期そのものは実測で1分ほどです）。昼以降の同期は、これまでどおりです。

正直に書いておくと、「採用0件の日は定期実行がやり直す」というふるまい自体は、今回は変えていません。時刻の順番を直して、同じ食い違いが起きにくくしただけです。

――――――――――――――――――――――――――――――――

🧰 今回のハーネス術：実測値と時刻を「残す」

■ 実測値はコミットメッセージに書く
1回目の前倒しのコミットには、変更内容だけでなく「8時50分開始では実測23分半かかっていた」という根拠を書いてもらいました。
あとで「なぜこの時刻なのか」を見直すとき、数字が残っていれば、その判断がまだ正しいかをすぐ確かめられます。この記事の数字も、そのコミットと決定ログから拾っています。

■ 時刻と順番はテストで固定する
3回目の変更では、定期実行の時刻と「トレンド同期 → 中長期 → 短期」の順番を、テストで固定してもらいました。
誰かがうっかり時刻をずらすと、テストが落ちて教えてくれます。締め切りのあるバッチほど、時刻は「設定値」ではなく「守るべき約束」として扱ったほうが安心です。
