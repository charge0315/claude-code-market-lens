# はじめに

日本株のAI銘柄スクリーニング＆継続学習端末**「ALPHA FORGE（アルファフォージ）」**を個人で開発・運用しています。開発には Claude Code を使っています。

前回は、構築プロンプト1枚から約25時間で一通り動くシステムが立ち上がった話を書きました。今回は、その2日後、**初めて本番の朝にAIピック（銘柄選定バッチ）を動かしたら、失敗したうえにバックエンド全体が応答しなくなった**ときの記録です。

原因は1つではなく、4つが重なっていました。どれも FastAPI や asyncio で外部APIを叩くシステムなら起こりうるものなので、原因と直し方をまとめます。

:::note info
**【要約】**
- データ提供APIの無料プランは直近12週間のデータが対象外だった（仕様どおりの400エラー）
- `async def` の中で同期のHTTP呼び出し（yfinance）を直接実行し、イベントループ全体が止まっていた → `asyncio.to_thread` で別スレッドへ
- 1銘柄の取得失敗が例外のまま上に伝わり、バッチ全体が500で落ちていた → 銘柄単位で `try/except` してスキップ
- 別サービス（ベクトル検索API）の起動忘れで、候補ごとに接続待ちが積み重なっていた → 起動チェックリストをルール化

※本記事はnote連載［ALPHA FORGE 開発秘話 #02］(https://note.com/featured_stocks/n/naf33466d4d8d) の技術的な部分を、エンジニア向けに再構成したものです。
:::

# 2. 症状：ピック生成が失敗し、設定画面まで開かない

2026年9月14日（月）の朝6時49分、画面にこう表示されました。

```text
ピック生成に失敗しました
```

ログには、株価データAPI（J-Quants）のエラーが2種類出ていました。

```text
J-Quants 400 /equities/bars/daily → Your subscription covers the following dates: 2024-06-22 ~ 2026-06-22
J-Quants 429 /equities/master → Rate limit exceeded
```

さらに、関係なさそうな設定画面も開かなくなっていました。調べると、バックエンドのプロセスはポート8002でLISTENしているのに、**どのエンドポイントもリクエストを処理していない**状態でした。

---

# 3. 原因① 無料プランの仕様（データ期間とレート制限）

400エラーの「2026-06-22 まで」は、当日（9/14）からちょうど約12週間前です。確認すると、当時の無料プランは**直近12週間を除く過去データ**が対象で、呼び出し回数の上限も厳しいものでした。

つまり契約切れではなく仕様どおりです。APIキーを差し替えても、制限はアカウントの契約プランに紐づくので変わりません。当日のデータで銘柄を選ぶバッチとは根本的に合わないため、有料プランに切り替えました（この判断は人間がしています）。

:::note warn
外部APIの `400` が「データ期間外」を示す場合、キーの更新やリトライでは直りません。エラーメッセージに出ている日付範囲と、プランの提供範囲を突き合わせるのが近道です。
:::

---

# 4. 原因② `async def` の中の同期I/Oがイベントループを止めていた

プランを変えても、バッチを動かすとまたバックエンド全体が固まりました。ここからはコードの問題です。

FastAPI のバックエンドは asyncio のイベントループ（1本のスレッド）で動いています。`async def` の中で**同期のネットワーク呼び出し**を直接実行すると、応答が返るまでループ全体が止まり、ほかのリクエストも処理されません。

該当箇所は2つありました。

- 候補銘柄ごとに財務データを取る `yf.Ticker(...).info`（同期）
- 特徴量構築のために、**東証の全銘柄**の価格を1件ずつ取るループ（同期。こちらが本命）

修正は、同期関数を `asyncio.to_thread` でスレッドへ逃がすだけです（以下のコードは実際の修正コミットからの抜粋です）。

```python:backend/services/scoring/fundamental_analyzer.py
async def get_fundamental_with_vault_fallback(ticker: str) -> dict[str, str | float | int | None]:
    # get_fundamental_data は yf.Ticker(...).info を同期的に叩く（ブロッキング I/O）ため、
    # to_thread に逃がさないとピック生成ループ全体でイベントループを占有してしまう。
    base = await asyncio.to_thread(get_fundamental_data, ticker)
    ...
```

```python:backend/services/learning/panel_feature_service.py
    # ユニバース全銘柄分の価格取得（同期 I/O）をイベントループ上で直接回すと、その間
    # 他の全リクエストが応答不能になる（1銘柄ずつ yfinance/J-Quants を叩くため長時間かかる）。
    panel = await asyncio.to_thread(_build_raw_universe_frame, tickers, set(wanted), price_loader)
```

修正後、バッチの実行中に別のエンドポイントを並行して叩いたところ、200ms未満で応答し続けることを確認しました。

:::note info
同じファイルの中でも、スコアリング本体（`_score_one`）は最初から `to_thread` で包まれていました。**一部だけ包み忘れる**のが典型的な漏れ方です。「`async def` の中で、`await` の付かない外部I/Oがないか」をレビュー観点にしておくと見つけやすくなります。
:::

# 5. 原因③ 1銘柄の失敗がバッチ全体を500で落としていた

イベントループの問題を直すと、今度はリクエストから109秒後に `500 Internal Server Error` が返りました。

トレースバックを見ると、ある1銘柄のデータ取得でサーキットブレーカー（連続失敗時に一時的に呼び出しを止める仕組み）が開き、`StockCircuitOpenError` が出ていました。検証中に問い合わせが集中したことも一因です。

ブレーカーが開くこと自体は正常な動作です。問題は、**スコアリングのループがその例外を受け止めず、候補全体の処理を中断していた**ことでした。ほかの箇所では「1銘柄の失敗で全体を止めない」方針になっていたのに、ここだけ抜けていました。

```python:backend/services/picks/pipeline.py
    for code in codes:
        try:
            fundamental = await get_fundamental_with_vault_fallback(code)
            ticker_rows = await fetch_per_ticker_champion_rows(code)
            ml_score_provider = combine_ml_score_providers(
                pool_provider, make_per_ticker_ensemble_provider(ticker_rows)
            )
            rec, atr, trend_score = await asyncio.to_thread(_score_one, code, fundamental, ml_score_provider)
        except Exception as e:  # noqa: BLE001 — 1銘柄の失敗（サーキットブレーカー・レート制限等）で全体を落とさない
            logger.warning("スコアリングに失敗（銘柄をスキップ）: %s — %s", code, e)
            continue
        scored.append((code, rec, atr, trend_score))
```

:::note warn
広く `except Exception` で握りつぶすと、原因が見えなくなる「静かな失敗」になりがちです。ここでは**銘柄コードと例外内容を WARNING でログに残し**、スキップしたことが後から追えるようにしています。
:::

①〜③の修正は、朝7時53分に1コミットにまとめました。

# 6. 原因④ 別サービスの起動忘れで「接続待ち」が積み重なった

修正後、短期ピックは Celery の worker 経由で約20分（1205.7秒）かけて完走し、3銘柄が採用、5銘柄が却下されました。

ところが中長期ピックを画面のボタンから実行すると、また「失敗しました」と表示されます。実際にはバックエンドは処理を続けていて、**フロント側のHTTP待ちが先にタイムアウトしていた**だけでした。それでも処理はなかなか終わりません。

原因を深掘りしてもらうと、関連ノートを探すベクトル検索API（別リポジトリで動かしている自作サービス）が起動していませんでした。候補銘柄ごとの検索呼び出しが**逐次実行**だったため、「接続失敗 → タイムアウト待ち」が候補の数だけ積み重なっていました。プロセスのCPU時間は4分強なのに、経過時間は40分を超えていました。

検索呼び出しは失敗しても空リストを返す作り（fail-soft）だったので、エラーにはならず、ただ遅くなるだけでした。そのため気づくのが遅れました。

:::note info
「CPU時間は短いのに経過時間が長い」ときは、計算ではなく**I/O待ち**を疑います。fail-soft な外部呼び出しは、失敗しても処理が止まらないぶん、遅延の原因として見落としやすくなります。
:::

# 7. 再発防止：起動チェックリストをAIのルールファイルに書く

同じ日の夕方、Claude Code が毎回最初に読むプロジェクトのルールファイル（`CLAUDE.md`）に、起動手順を追記しました。要旨は次のとおりです。

```markdown:CLAUDE.md（要旨）
## ローカル起動（「システム起動して」と言われたら）
以下をすべて確認し、動いていないものだけ起動する。
- frontend (3001) / backend (8002)
- Redis（Celery のブローカー）
- celery worker（Windows では --pool=solo 必須）
- ベクトル検索API（未起動だとナレッジ検索が全銘柄で接続失敗・タイムアウトし、ピック生成が大幅に遅延する）
```

今は毎朝「システム起動して」と伝えるだけで、依存サービスまで含めて上から順に確認・起動されます。

# 8. 役割分担（Human in the Loop）

この朝、誰が何をしたかを整理しておきます。

| 担当 | やったこと |
|---|---|
| 人間 | 異変に気づく（「失敗しました」「設定画面がでないのもそのせい？」「根本原因をさぐってください」）、有料プランへの切り替え（契約・支払い）を決める |
| AI（Claude Code） | ログ解析、応答時間の実測、同期I/O 2か所と例外処理の漏れ1か所の特定・修正、ローカルCI相当のチェック後にコミット |

「根本原因をさぐってください」と頼んだことで、④の起動忘れまでたどり着けました。症状ではなく原因を求める頼み方は、AIエージェントに調査させるときの基本だと感じています。

# まとめ

- 外部APIの400は、まず提供期間やプランの仕様を疑う
- `async def` の中の同期I/Oは `asyncio.to_thread` へ。包み忘れがないかをレビュー観点にする
- バッチの「1件の失敗」は、ログを残したうえでスキップし、全体を道連れにしない
- fail-soft な外部呼び出しは遅延の原因になりやすい。依存サービスの起動確認は手順（ルールファイル）にする

次回は、AIに渡した「構築プロンプト」の中身と、機能一覧より先に「約束」と「作らないもの」を書く設計の考え方を紹介します。
