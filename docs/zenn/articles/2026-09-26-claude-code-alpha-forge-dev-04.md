締め切りが「相場の開始時刻」で決まっているバッチを、書いたことはありますか。

日本株のAI銘柄スクリーニング＆継続学習端末「**ALPHA FORGE（アルファフォージ）**」を、Claude Code と二人三脚で個人開発しています。朝いちばんの仕事は、寄り付き前に銘柄を抽出しておくこと。東証が開く9時は、1秒も延びてくれません。今回は、この「9時の壁」に3回ぶつかった話です。

:::message
**【要約：この記事で伝えたいこと】**
1. 08:50 開始の朝バッチは、中長期の抽出だけで実測 **23分24秒**。寄り付きの9時に間に合っていなかった
2. 処理を速くする前に「早く始める」ことで解決し、開始時刻を **08:50 → 07:40 → 07:30 → 07:00** と3回前倒しした
3. 3回目は、手動実行と定期実行の組み合わせで「公開済みの記事と台帳が食い違った」のがきっかけ。時刻と実行順はテストで固定した
:::

# 構成：Celery beat ＋ Windows の solo ワーカー

朝の抽出は Celery beat（定期実行スケジューラ）から発火し、Celery ワーカーが実行します。開発・運用環境は Windows で、ワーカーは `--pool=solo` で動かしています（Windows では prefork プールが使えないため）。

```powershell
.venv\Scripts\celery.exe -A backend.celery_app worker --pool=solo --loglevel=info
```

`solo` はタスクを**1件ずつ直列に**処理します。中長期と短期の2つの抽出タスクを2分ずらして登録していても、中長期が終わるまで短期は順番待ちになるだけです。


# 事件：「市場がひらくのに間に合わないね」

2026年9月16日の9時7分、画面を見ていた私が Claude Code に送ったのは、この一言でした。

> ピックに時間がかかっていて、市場がひらくのに間に合わないね

Claude Code が2つのタスクの完了を見届けて所要時間を報告してくれた結果が、こちらです。

| タスク | 開始 | 完了 | 所要時間 |
|---|---|---|---|
| 中長期の抽出 | 08:50 | 09:13:22 | 約23分24秒（1403秒） |
| 短期の抽出 | 中長期の完了待ち | 09:15:03 | 約1分31秒（91秒） |

中長期は、全銘柄の価格取得と LLM による分析が直列に並ぶため時間がかかります。短期は直前に取得したデータを使えたので短く済みましたが、それでも完了は寄り付きの15分後でした。

気づいたのは、朝の画面を見ていた人間です。テストはすべて通っていて、エラーも出ていない。ただ「相場の時計」で見ると遅すぎる。原因を数字で示したのは Claude Code でした。


# 判断：速くする前に、早く始める

遅いなら速くする、のが普通の発想です。並列化、キャッシュ、待ち時間の削減。どれもやりたくなる改善ですが、変更は大きくなり、毎朝のバッチを壊すリスクも増えます。

「間に合わせる」だけなら、開始時刻を早めれば済みます。Claude Code が実測にもとづいて余裕を見た時刻を提案し、私が採用しました。

![朝の銘柄抽出バッチの開始時刻の変遷](/images/alpha-forge-dev-04/01_schedule_timeline.png)
*朝の銘柄抽出バッチの開始時刻の変遷（バーの長さは9/16の実測23分半を当てはめた目安）*

1. 〜9月16日：08:50 開始。中長期だけで23分24秒かかり、寄り付きに間に合わない
2. 9月17日：07:40 開始（短期は 07:42）へ前倒し
3. 同じ9月17日：07:30 へさらに前倒し。08:05 に動く「note下書きの自動生成」が抽出結果を使うようになったため
4. 9月25日：07:00 へ前倒し（次の章）

性能改善をやめたわけではありません。「今日の問題は、今日中に安全に直せるやり方で先に止める。速くするのはそのあと」という順番を決めた、ということです。


# 落とし穴：beat の crontab は UTC で書く

時刻の変更自体は1行ですが、このプロジェクトでは beat のスケジュールを UTC で評価しているため、JST を UTC に換算して書いています（JST は夏時間がないので、単純に9時間引くだけです）。

```python:backend/celery_app.py（抜粋）
_BEAT_SCHEDULE: dict[str, dict[str, object]] = {
    "run-picks-mid-term": {
        "task": "backend.tasks.run_picks_task",
        "args": ("mid_term",),
        "schedule": crontab(hour=22, minute=0),  # JST 07:00（寄り付き前、記事作成より前）
    },
    "run-picks-short-term": {
        "task": "backend.tasks.run_picks_task",
        "args": ("short_term",),
        "schedule": crontab(hour=22, minute=2),  # JST 07:02（solo worker で直列実行のため実質は順番待ち）
    },
    # ...
    "sync-trends-morning": {
        "task": "backend.tasks.sync_trends_task",
        "schedule": crontab(hour=21, minute=45),  # JST 06:45（ピック生成 07:00 の前）
    },
}
```

`hour=22` が「前日の22時」ではなく「JST 7時」を意味するのは、コメントがないと必ず誰かが誤読します。換算後の JST をコメントに書くのは必須にしています。


# 3回目：公開済みの記事と台帳が食い違った

3回目の前倒しは、9月25日の朝に起きた出来事がきっかけです。

1. 06:52、抽出を手動で実行した。中長期は候補がすべて見送られ、0件だった
2. その結果をもとに、朝の記事を書いて公開した
3. 07:30、定期実行が動いた。「今日の中長期はまだ採用が1件もない」と判断して、中長期の抽出をやり直した
4. 1回目は AI の自信度38%で見送られていた銘柄が、2回目は40%で採用ラインをちょうど越えた

定期実行側には「その日の分がもう出ていれば二重に作らない」ガードがありますが、判定しているのは**採用された件数**です。採用0件の日は「まだ出ていない」と見なされ、やり直しが走ります。その結果、記事には「中長期は0件」、台帳には1件、という食い違いが生まれました。

対処として、私が決めたのは「記事を書く前に定期実行を終わらせておく」ことです。開始を 07:00 に前倒ししました。

:::message alert
前倒しには副作用がありました。抽出の材料に使う朝のトレンド同期は 07:13 に動いていたため、抽出を7時に早めると当日朝の情報が間に合いません。私の判断で、朝の分だけ同期を `sync-trends-morning`（06:45、同期の実測は約1分）として切り出しました。昼以降の同期は据え置きです。

なお、「採用0件の日は定期実行がやり直す」ふるまい自体は今回変えていません。時刻の順番を直して、同じ食い違いを起きにくくしただけです。
:::


# 時刻と実行順をテストで固定する

締め切りのあるバッチでは、時刻は「設定値」ではなく「守るべき約束」です。うっかり戻らないよう、時刻と実行順をテストで固定してもらいました。

```python:backend/tests/test_beat_schedule.py（抜粋）
_JST_OFFSET_HOURS = 9


def _jst_hour_minute(entry_name: str) -> tuple[int, int]:
    schedule = celery_app.conf.beat_schedule[entry_name]["schedule"]
    (utc_hour,) = schedule.hour
    (minute,) = schedule.minute
    return (utc_hour + _JST_OFFSET_HOURS) % 24, minute


def test_mid_term_picks_run_at_0700_jst() -> None:
    assert _jst_hour_minute("run-picks-mid-term") == (7, 0)


def test_morning_trend_sync_runs_before_picks() -> None:
    assert _jst_hour_minute("sync-trends-morning") == (6, 45)
    assert _jst_hour_minute("sync-trends-morning") < _jst_hour_minute("run-picks-mid-term")
```

テストの中でも UTC → JST に換算して比べているので、テストを読むだけで「何時に動くか」が分かります。


# 実測値はコミットメッセージに残す

1回目の前倒しのコミットには、変更内容だけでなく根拠の数字を書いてもらいました。

```text:コミットメッセージ（2026-09-17）
fix: AI銘柄ピック生成の開始時刻を寄り付き前に間に合うよう前倒し

08:50 JST開始では実測23分半（中長期のみ）かかり、solo workerの直列実行と
合わせて寄り付き09:00に完了が間に合っていなかった。実測を基に安全マージンを
確保し、07:40/07:42 JST開始に変更する。
```

あとで「なぜこの時刻なのか」を見直すとき、数字が残っていれば判断がまだ正しいかをすぐ確かめられます。この記事の数字も、コミットと決定ログ、当時の会話ログから拾っています。


# まとめ

1. 締め切りが外部の時計（ここでは東証の9時）で決まるバッチは、まず**実測**する
2. 間に合わないなら、性能改善より先に**開始時刻の前倒し**で止血する
3. Celery の `--pool=solo` では、タスクを数分ずらしても**直列の順番待ち**になるだけ
4. beat の crontab を UTC で書くなら、**換算後の JST をコメントに書く**
5. 時刻と実行順は**テストで固定**し、根拠の実測値は**コミットメッセージに残す**

気づいたのは相場の時計で生きる人間、実測して案を出したのは Claude Code、採用して線を引いたのは人間。この分担は、今回も変わりませんでした。
