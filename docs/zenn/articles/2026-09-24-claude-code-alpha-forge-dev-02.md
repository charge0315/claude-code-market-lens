# はじめに

日本株のAI銘柄スクリーニング＆継続学習端末「**ALPHA FORGE（アルファフォージ）**」を、Claude Code と二人三脚で個人開発しています。

前回は「構築プロンプト1枚から、約25時間で一通り動くシステムが立ち上がった」話でした。ただ、それは話の半分です。今回は、**完成から2日後、初めて本番の朝にAIピックを動かしたら全滅した**ときの障害対応記です。

:::message
**【要約：この記事で伝えたいこと】**
- 障害の原因は1つではなく、**データ契約・同期I/O・例外処理・起動忘れ**の4つが重なっていた
- 異変に気づき、お金の判断をしたのは人間。原因を突き止めて直したのはAI
- AIの「完成」は、人間が本番で使って確かめて初めて完成になる
:::

# 朝6時49分「ピック生成に失敗しました」

2026年9月14日、月曜日。朝6時半にサーバーを起動し、いよいよ初めての本番ピックです。ボタンを押して返ってきたのは、この一文でした。

```text
ピック生成に失敗しました
```

Claude Code にログを見てもらうと、株価データAPI（J-Quants）から2種類のエラーが出ていました。

:::details 当時のエラーログ（抜粋）
```text
J-Quants 400 /equities/bars/daily → Your subscription covers the following dates: 2024-06-22 ~ 2026-06-22
J-Quants 429 /equities/master → Rate limit exceeded
J-Quants fetch_all_listed_stocks failed: J-Quants server error 429: /equities/master
```
:::

ついでに、気になっていたことを聞きました。

> 「設定画面がでないのもそのせい？」

これが大当たりでした。設定画面どころか、**バックエンド全体がリクエストに応答しなくなっていた**のです。


# 壁その1：無料プランでは「今日」のデータが取れない

APIキーを更新してみても変わりません。Claude Code の見立ては「期間の制限はキーではなく、アカウントの契約プランに紐づく」でした。

> 「Freeプランじゃだめなのかな」

公式サイトで確認してもらうと、当時の無料プランは**直近12週間を除く過去データ**が対象でした。9/14 から12週間さかのぼると、ちょうどエラーに出ていた 6/22 前後です。契約切れではなく、仕様どおりに「今日のデータはお渡しできません」と言われていたわけです。

毎朝その日のデータで銘柄を選ぶ端末には致命的なので、有料プランに切り替えました。

:::message alert
有料プランへの切り替えは、契約と支払いを伴う判断です。AIは選択肢と理由を示してくれますが、決めて支払うのは人間です。
:::


# 壁その2：イベントループという「1本道」をふさいだ同期I/O

プランを変えても、バッチを動かすとまたバックエンドが固まりました。ここで Claude Code が、コード側の原因を突き止めます。

FastAPI は asyncio のイベントループ、いわば**1本の道**で多くのリクエストをさばいています。誰かが道の真ん中で立ち止まると、後ろは全員止まります。

立ち止まっていたのは、`async def` の中で直接呼ばれていた**同期のネットワーク呼び出し**でした。

- 候補銘柄ごとに財務データを取る `yf.Ticker(...).info`
- 特徴量のために**東証の全銘柄**の価格を1件ずつ取るループ（こちらが本命）

直し方はシンプルで、`asyncio.to_thread` で別スレッドに回すだけです（実際の修正コミットからの抜粋）。

```python:backend/services/learning/panel_feature_service.py
    # ユニバース全銘柄分の価格取得（同期 I/O）をイベントループ上で直接回すと、その間
    # 他の全リクエストが応答不能になる（1銘柄ずつ yfinance/J-Quants を叩くため長時間かかる）。
    panel = await asyncio.to_thread(_build_raw_universe_frame, tickers, set(wanted), price_loader)
```

```python:backend/services/scoring/fundamental_analyzer.py
    # get_fundamental_data は yf.Ticker(...).info を同期的に叩く（ブロッキング I/O）ため、
    # to_thread に逃がさないとピック生成ループ全体でイベントループを占有してしまう。
    base = await asyncio.to_thread(get_fundamental_data, ticker)
```

直したあとは、バッチの実行中でもほかのエンドポイントが200ms未満で応答し続けるようになりました。同じファイル内のスコアリング本体はきちんと `to_thread` で包まれていたので、「一部だけ包み忘れる」という典型的な漏れ方でした。


# 壁その3：1銘柄の不調が、全員を道連れにする

一安心と思ったら、今度はリクエストから109秒後に `500 Internal Server Error`。

原因は、ある1銘柄のデータ取得でサーキットブレーカー（連続で失敗したら一時的に問い合わせを止める安全装置）が開いたことでした。安全装置が働くこと自体は正常です。問題は、**その1銘柄の例外を誰も受け止めず、バッチ全体を失敗させていた**ことでした。

```python:backend/services/picks/pipeline.py
    for code in codes:
        try:
            fundamental = await get_fundamental_with_vault_fallback(code)
            ...
            rec, atr, trend_score = await asyncio.to_thread(_score_one, code, fundamental, ml_score_provider)
        except Exception as e:  # noqa: BLE001 — 1銘柄の失敗で全体を落とさない
            logger.warning("スコアリングに失敗（銘柄をスキップ）: %s — %s", code, e)
            continue
        scored.append((code, rec, atr, trend_score))
```

スキップした銘柄と理由は WARNING でログに残し、「静かな失敗」にはしていません。ここまでの3つの修正を、朝7時53分に1コミットにまとめました。


# 壁その4：起動し忘れた検索サービス

修正後、短期ピックは Celery の worker で約20分かけて完走しました（3銘柄採用、5銘柄却下）。

ところが中長期ピックは、画面から実行するとまた「失敗しました」。実はバックエンドは裏で処理を続けていて、画面側のHTTP待ちが先にタイムアウトしていただけでした。それでも、待てど暮らせど終わりません。

> 「どうかな」
> 「おわった？」

市場が開いても終わらないので、9時49分にこう頼みました。

> 「AIピックに失敗しています。根本原因をさぐってください」

見つかったのは4つ目の原因でした。関連ノートを探すベクトル検索API（別に動かしている自作サービス）が起動しておらず、候補銘柄ごとに「つながらない → タイムアウトまで待つ → 諦める」を**1件ずつ順番に**繰り返していたのです。CPU時間は4分強なのに、経過時間は40分を超えていました。

検索呼び出しは失敗しても空の結果を返す作りだったので、エラーにはならず、ただ遅くなるだけでした。検索サービスを起動すると、中長期ピックは実は完了していたことも分かりました。

初めての朝のAIピックは、結局、寄り付きには間に合いませんでした。

# 今回のプロンプト／ハーネス術

## 症状ではなく「根本原因」を頼む

「失敗しています」だけだと、目の前のエラーへの対処で終わりがちです。「根本原因をさぐってください」と一言添えるだけで、ログや処理時間の内訳まで掘り下げてくれました。4つ目の原因は、この一言で見つかっています。

## 口癖をルールファイルに書く

同じ日の夕方、Claude Code が毎回最初に読むルールファイル（`CLAUDE.md`）に、起動チェックリストを追記しました。

:::details CLAUDE.md の該当部分（要旨）
```markdown
## ローカル起動（「システム起動して」と言われたら）
以下をすべて確認し、動いていないものだけ起動する。
- frontend (3001) / backend (8002)
- Redis（Celery のブローカー）
- celery worker（Windows では --pool=solo 必須）
- ベクトル検索API（未起動だとナレッジ検索が全銘柄で接続失敗・タイムアウトし、ピック生成が大幅に遅延する）
```
:::

今では毎朝「システム起動して」の一言で、依存サービスまで上から順に確認してくれます。


# まとめと次回予告

- 外部APIの400は、まず提供期間やプランの仕様を疑う
- `async def` の中の同期I/Oは `asyncio.to_thread` へ
- 1件の失敗は、ログを残してスキップし、全体を道連れにしない
- 失敗しても止まらない外部呼び出しは、遅延の原因として見落としやすい

前回「私の入力は『次』『続行』の2語」と書きましたが、あの2語で済んだのには理由があります。AIに作業を渡す前日に、人間が「約束」を書き切っていたからです。次回は、その構築プロンプトの中身を紹介します。
