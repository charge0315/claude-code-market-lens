# はじめに

日本株のAI銘柄スクリーニング＆継続学習端末「**ALPHA FORGE（アルファフォージ）**」を、Claude Code と二人三脚で個人開発しています。

第1話で「私の入力はほとんど『次』『続行』の2語だった」と書きました。今回はその種明かしです。あの2語で済んだのは、AIに作業を渡す前に、**人間が「約束」を書き切っていたから**でした。

:::message
**【要約：この記事で伝えたいこと】**
- 最初の指示は「〇〇を作って」ではなく、Markdown 1枚の「構築プロンプト」だった
- 中心は機能一覧ではなく「作らないもの」「厳守ルール」「未決事項」「受け入れ基準」の4つ
- プロンプトは使い捨てにせず、運用で得た知見を書き足して次の開発の原本として育てている
:::

# 構築プロンプトの全体像

2026年9月10日、空のフォルダに1枚のMarkdownを置き、Claude Code に「このプロンプトに従ってプロジェクトを立ち上げてください」と頼みました。翌朝6時43分には、Claude Code が書いた計画ドキュメント一式（PRD／アーキテクチャ／システム設計／タスクリスト）が最初のコミットとして記録されています。

プロンプトの章立ては次のとおりです。

| 章 | 内容 |
|---|---|
| 0 | エレベーターピッチ（一言で何を作るか） |
| 1 | スコープ（In Scope ／ **Out of Scope＝明示的に作らない**） |
| 2 | 継続学習ループ（**最優先で設計する**） |
| 3〜8 | AI思考の可視化、データソース、アーキテクチャ、スコアリング、通知、UI |
| 9 | 日本株ドメインルール（**厳守**） |
| 10 | 非機能要件（テスト、セキュリティ、CI、Git運用） |
| 11 | 決定事項と**残る未決事項** |
| 12 | 運用フェーズで得た知見（後から追記） |
| 13 | 開発フェーズ計画（各フェーズに完了条件） |
| 14 | **受け入れ基準（Definition of Done）** |
| 15 | Claude Code への作業指示 |

画面や機能の要件もありますが、分量で見ると「決まりごと」と「線引き」のほうが多いファイルです。


# 約束その1：作らないものを先に書く

AIは頼まれていない機能まで気を利かせて作りがちです。そこでスコープの章に「明示的に作らない」ものを並べました（要旨）。

```markdown:構築プロンプト §1（抜粋）
### Out of Scope（明示的に作らない）
- ブローカーへの実発注は一切行わない。アプリは提案と通知のみ。約定は人間が別途手動で行う。
- 米国株・暗号資産・FX・先物。
- 投資助言業に該当する「個別断定的な投資勧誘」。出力は必ず「分析結果・参考情報」として提示し、免責を UI に常設。
- 資金移動・入出金・自動売買・自動ポジション管理。
```

1行目は端末の性格そのものを決める一文です。どれだけ便利な自動化を思いついても、この線を越える提案は出てきませんでした。

もう1つ効いたのが、前身の自作ツールについての一文です。

```markdown:構築プロンプト 冒頭（要旨）
既存プロジェクト（前身ツール）は再利用元。ドメインロジック・データ取得層・スコアリングは
移植を第一選択とし、ゼロから書き直さない。
```

:::message alert
AIはゼロから書くのが速くて得意です。書いておかないと、動いている部品まで作り直してしまいます。
:::


# 約束その2：破ってはいけないルールは「厳守」と書く

日本株には、海外製のひな形のままだと間違える決まりごとがあります。

```markdown:構築プロンプト §9（抜粋）
## 9. 日本株ドメインルール（厳守）
- 時刻はすべて JST。東証大引け 15:00。
- 銘柄コードは 4 桁（例 7203）。.T サフィックスを付けない。
- 騰落色 赤 = 上げ / 緑 = 下げ。
```

設計の芯になる約束も、同じ強さで書いています。

- AIが売買銘柄を提案するなら「推奨買値／損切値／推奨売値」の3値を必須とし、`損切 < 現在値 < 売値` かつ `損切 < 買値 < 売値` をサーバ側で検証する
- 外部由来のテキストをLLMプロンプトへ注入しない（構造化フィールドのみ）
- モデルの入れ替えは提案のみ。差し替えは人間の承認で行う

これらは後に、Claude Code が毎回最初に読むルールファイル `CLAUDE.md` にも引き継がれています。


# 約束その3：未決事項を「未決」と書く

いちばん意外だったのがこの章の効き目です。決めきれていないことを、正直に4つ書いておきました。

```markdown:構築プロンプト §11（要旨）
### 残る未決事項（P0 の計画時にユーザーへ確認）
1. ペーパートレード期間 — 昇格ゲートに必要な最小日数（暫定 20 営業日で提案）
2. 移植 vs 新規 — どのモジュールを移植し、どこから新規設計とするか
3. Web Push の対象ブラウザ / PWA 化の要否
4. LLM プロバイダ / モデル構成、コスト上限
```

作業指示の章には、こう添えました。

```markdown:構築プロンプト §15（抜粋）
1. まず P0 を実行し、plans/ に計画ドキュメントを生成、§11 の未決事項をまとめてユーザーに確認する。
   未決事項が残る項目は feature flag OFF のスタブで進める。
```

すると実際に、計画フェーズで Claude Code から質問が返ってきました。私の回答は決定ログにこう残っています。

| 未決事項 | 人間の回答 |
|---|---|
| ペーパー成績の最小日数 | 20営業日（暫定案どおり） |
| Web Push / PWA | デスクトップ常駐のみ、PWA化はしない |
| LLM構成・コスト上限 | 前身ツールと同一構成を踏襲 |

移植範囲は、P0 の棚卸しでAIが提案する形にしました。AIが勝手に決めてしまうと、あとで気づいて直すのは人間です。**「まだ決めていない」と書けば、AIは決める前に聞いてくれます。**


# 約束その4：完成の条件を先に決める

受け入れ基準（Definition of Done）は13項目のチェックリストにしました（抜粋）。

```markdown:構築プロンプト §14（抜粋）
- [ ] 中長期・短期それぞれのピックが、根拠 + 確度 + 推奨買値 / 損切値 / 推奨売値 付きで生成される。
- [ ] すべての予測が台帳化され、決着後に評価指標が自動更新される。
- [ ] 再学習が定期 + ドリフトで発火し、challenger が shadow で並走、昇格は提案のみ。
- [ ] アプリはブローカー発注を一切行わない。
- [ ] backend / frontend の CI がローカルで全通し。テストカバレッジ 80% 以上。
```

フェーズ計画（P0 調査＆計画 〜 P8 仕上げ）の各行にも「完了条件」の列を付け、フェーズが終わるたびにコミットとローカルCI全通しを求めました。

「完成しました」の判定がぶれないのは、この基準があるからです。第1話の「次」「続行」は、この基準に照らして「次のフェーズへどうぞ」と言っていただけ、とも言えます。


# プロンプトは「育てる」もの

構築プロンプトは一度使って終わりにしていません。運用を始めてから分かったことを、§12「運用フェーズで得た知見」として後から書き足しています。

:::details §12 に追記した項目
- マルチLLMプロバイダの動的選択とシャドウ並走
- Point-in-Time（予測時点で確定していた情報だけ）のファンダメンタル／センチメント保存
- note下書きの自動生成とプレーンテキスト執筆フロー
- 日次パイプラインログの自動集約
- 学習の並列化（ProcessPoolExecutor）
- celery-beat を安全に自動起動するための冪等ガード（休場日スキップ・当日生成済みスキップ）
:::

9月22日には、別に作っていた似たような構築プロンプト集をこの1枚に統合し、古いほうは削除しました。次に同種のシステムを作るときは、この1枚から始めれば、今回ぶつかった壁の何割かは最初から避けられるはずです。


# 役割分担

| 担当 | やったこと |
|---|---|
| 🧑 人間 | 約束・作らないもの・受け入れ基準を書く。未決事項を「未決」と正直に書く。質問に答えて方針を決める |
| 🤖 Claude Code | 未決事項を質問として返す。計画ドキュメントに落とし込む。約束を守りながらフェーズごとに実装・検証する |

「次」「続行」の2語は、人間が何もしていなかった証拠ではなく、前日に書いた約束が効いていた証拠でした。


# まとめと次回予告

機能一覧より先に、次の4つを書く。

1. 作らないもの（Out of Scope）
2. 破ってはいけないルール（「厳守」と明記）
3. 未決事項（「計画時に確認すること」「決まるまではスタブで」と添える）
4. 完成の条件（受け入れ基準＋フェーズごとの完了条件）

あわせて「調査 → 計画 → TDD → レビュー → 検証 → コミット」という進め方と、「コミット・push・外部送信は人間の確認を取る」という線引きも、最初に書いておきます。AIに任せる範囲と、人間が止める場所を先に決めておくためです。

次回は事件簿に戻り、「寄り付きに間に合わない！ 23分半かかったピック生成」の話です。
