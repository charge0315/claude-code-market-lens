### 1.8 Point-in-time 特徴量スナップショット（🆕 P29）

ML 学習に Vault 由来のファンダメンタル・ニュースセンチメントを載せるための **時点整合（point-in-time, PIT）台帳**。

**なぜ新テーブルが要るか**: Vault `Tickers/<code>_<name>.md` は日次スクレイピングで**上書き更新される「現在値」ファイル**であり、過去バージョンを保持しない（`services/vault/brand_notes_service.py`）。`panel_feature_service.build_panel` は過去最大 500 営業日（`_DEFAULT_PANEL_BDAYS`）の断面パネルを組むため、「今日の frontmatter 値」を過去の各営業日行へそのまま結合すると **未来情報が過去の学習行へ漏れる（lookahead bias）**。CLAUDE.md の「ウォークフォワード検証必須（時系列 CV のみ、未来リーク構造排除）」に真っ向から反するため、**今日から先の値を日次で追記して貯める**以外に正しい実装経路はない（過去分は原理的に復元不能）。

**`pit_fundamental_snapshots`** — 1 営業日 × 1 銘柄 = 1 行の append-only 台帳。

| 列 | 型 | 説明 |
|:--|:--|:--|
| `snapshot_date` | TEXT PK(1) | **観測日**（JST 営業日 `YYYY-MM-DD`）。学習時はこの値だけを as_of 結合キーに使う |
| `code` | TEXT PK(2) | 4 桁コード |
| `source` | TEXT | `vault_frontmatter` / `shikiho` / `jquants` / `yfinance`（§3.7 の PIT プロバイダ識別子） |
| `data_as_of` | TEXT NULL | **提供元が主張する基準日**（frontmatter の `data_as_of` / `close_date`）。`snapshot_date` との差（`data_staleness_days`）自体を特徴量にする |
| `per_forecast` / `pbr` / `roe` / `equity_ratio` / `dividend_yield_forecast` / `eps_forecast` / `bps` / `market_cap_oku` | REAL NULL | `BrandNote` の財務指標をそのまま列にする（型変換・プレースホルダ正規化は `brand_notes_service._coerce_float` 済みの値） |
| `shares_outstanding` | INTEGER NULL | |
| `last_earnings_date` / `last_earnings_type` | TEXT NULL | `days_since_earnings` の導出元（決算跨ぎの情報量変化を捉える） |
| `sector33` / `sector17` / `scale_cat` / `market` | TEXT NULL | 断面統計（セクター相対）の分母 |
| `extra` | TEXT(JSON) NULL | 四季報有効化（`SHIKIHO_ENABLED=true`）後の構造化フィールドをスキーマ変更なしで足すための拡張枠。**数値・enum のみ。外部由来の自由記述テキストは絶対に入れない** |
| `created_at` | TEXT | |

インデックス: `(code, snapshot_date)`。**同一 `snapshot_date` 内の再実行は UPSERT で上書き可、過去日の行は不変**（append-only の PIT 台帳としての不変条件。過去日を書き換える経路はコード上に持たない）。

**`pit_sentiment_snapshots`** — センチメントの PIT 台帳。ソース単位で行を分ける（被覆率がソースごとに大きく違うため）。

| 列 | 型 | 説明 |
|:--|:--|:--|
| `snapshot_date` / `code` / `source` | TEXT PK | `source` = `keyword`（`scoring/sentiment_analyzer.py`、LLM 不要・広く取れる）/ `llm`（`scoring/llm_news_sentiment_service.py`、コスト制約で少数のみ） |
| `news_count` | INTEGER | 対象見出し件数（0 件も 0 として記録する。「ニュースが無かった」ことも情報） |
| `keyword_positive` / `keyword_negative` / `keyword_score` | REAL NULL | `source='keyword'` のみ |
| `llm_sentiment_label` | TEXT NULL | `strongly_negative` … `strongly_positive` の 5 値 enum（`source='llm'` のみ） |
| `llm_sentiment_score` / `llm_impact_score` / `llm_confidence` | REAL NULL | −1.0〜+1.0 / 0–100 / 0–100 |
| `created_at` | TEXT | |

**`reasoning`（自由記述）は列として持たない**。`llm_news_sentiment_service` のモジュール境界（enum/number のみ転送）を DB スキーマの側でも強制するため — 一度でも学習テーブルへ生テキストが入ると、以後の特徴量エンジニアリング・ablation・UI 表示のどこかで LLM プロンプトへ再流入する経路が生まれる（CLAUDE.md「間接インジェクションのロンダリング」）。人間向けの `reasoning` は従来どおり `prediction_ledger.rationale_struct.news_sentiment` にのみ残す。

マイグレーションは `0010_pit_snapshots`（`0009_daily_notes` の次）。

### 1.9 `prediction_ledger.feature_snapshot` の粒度拡張（🔧 P29）

現行の `services/inference/orchestrator.py::_feature_snapshot()` は `score_breakdown`（**集約後**の technical/fundamental/sentiment 各 0–100）・`technical_signals` / `fundamental_signals` / `sentiment_average` / `ml_prediction_rate` / `trend_score` / `atr_14` / `current_price` のみを保存し、**Vault frontmatter の生の財務指標（PER/PBR/ROE の実数値）も LLM センチメントの生フィールドも入っていない**（後者は `rationale_struct`（人間向け表示専用）にしか無い）。このままでは将来「生特徴量で遡って再学習する」ことが台帳からは不可能で、`registry/drift.py` の PSI 監視も集約後スコアの粒度でしか動かない。

P29 で `pit_fundamental` / `pit_sentiment` の 2 サブ辞書（数値・enum のみ）を `feature_snapshot` へ追加する。`drift.MONITORED_FEATURES` は dotted path で引く実装（`pl.list_feature_values`）なので `pit_fundamental.per_forecast` 等をそのまま監視対象に足せる。

## 3. 主要アルゴリズム設計

### 3.1 推論オーケストレータ（stage DAG, N4）

```
run(symbol, horizon_type) -> Pick | Rejected
  stage collect     : data/ + vault/ から特徴量素材を集める。各ソースの成否を trace へ
  stage subscore    : scoring/ で technical/trend/fundamental/sentiment を 0–100。SHAP 寄与を trace へ
  stage llm_overlay : anthropic_client の forced tool-use。トークンを stream して trace へ
  stage synthesis   : recommender で composite_score/concordance/direction。source_contributions を算出
  stage bracket     : ATR・支持抵抗・RR 比から entry/stop/target。confidence_raw を算出
  stage verify      : stop<price<target かつ stop<entry<target。E1〜E3 ハード除外。calibration 適用 -> confidence
  -> prediction_ledger へ書き込み（is_shadow=0）。challenger があれば shadow で再実行し shadow_predictions へ
```

- 各 stage は「既存の移植サービスを呼ぶだけの薄いラッパ」。stage 間は `frozen` な中間 DTO を渡す。
- stage 失敗は trace に `failed` を記録し、以降を skip（ピックは `rejected` 扱い、理由付き）。
- トレースは逐次 `inference_traces` へ INSERT（リプレイ用）。SSE はこの INSERT をトリガに配信。

### 3.2 確度の事後較正（CL-7, N3）

- 教師データ: `pick_outcomes`（決着済み、horizon 別）。`confidence_raw` → 実現勝敗。
- 手法: サンプル数に応じて **isotonic**（十分なとき）/ **Platt**（少数のとき）を選択。horizon_type × direction ごとに較正器を学習し `data/calibrators/` に保存。
- 台帳が薄い初期（決着 n 小）は恒等写像へフォールバック（`confidence = confidence_raw`）し、`calibration_curves` に「未較正」フラグ。
- UI へ出すのは較正後 `confidence` と、同 `confidence_bucket` の過去実測勝率（`pick_outcomes` 集計）。

### 3.3 昇格ゲート（CL-6, N1）

```
evaluate(lane, challenger_version):
  champion = model_champions[lane].champion_version
  holdout_delta   = metric(challenger, holdout) - metric(champion, holdout)   # walk-forward, 時系列 CV のみ
  calib_regressed = calib_error(challenger) > calib_error(champion) + ε
  paper_perf_delta, paper_days = paper_perf(challenger) - paper_perf(champion) # shadow の擬似執行
  if paper_days < 20: verdict = hold  # 最小ペーパー成績日数（確定事項）
  elif holdout_delta > 0 and not calib_regressed and paper_perf_delta >= 0: verdict = propose_promote
  else: verdict = reject if holdout_delta < 0 else hold
  記録 model_promotions（applied=0）。MODEL_AUTO_PROMOTE=false（既定）では API 承認でのみ champion 差し替え
```

### 3.4 ドリフト検知（CL-4, N5）

- 特徴量ごとに baseline window（学習期間）と current window（直近 N 営業日）の分布を 10 分位 bin 化し **PSI** を計算。
- `PSI > 0.2` の特徴量が閾値本数を超える or 直近 N 件の予測精度（`eval_snapshots` の rolling）が既定比で劣化 → `triggered_retrain=1` で追加再学習タスクを enqueue。
- ドリフト結果は `drift_snapshots` へ。UI（モデルラボ）に PSI 推移を表示。

### 3.5 決着記録バッチ（CL-2）

- Market Lens `pick_outcome_service` の「後追い解決」パターンを踏襲: `run_date` を古い順に 1 つ選び、保有期間 + 約定窓 + バッファ経過分のみ解決。
- 拡張: 1 ピックにつき `horizon_days ∈ {1,2,3}`（短期）/ `{5,20,60}`（中長期）で複数行。yfinance 日次 OHLC で指値約定 → トリプルバリア。MFE/MAE と `first_hit`、TOPIX 超過を算出。

### 3.6 再学習スケジュール（celery-beat）

| タスク | 時刻（JST）目安 | 内容 |
|:--|:--|:--|
| ピック生成（中長期・短期） | 08:50 | 推論オーケストレータ → Ledger。shadow 並走 |
| 保有監視 | 09:00–15:30 の周期 | 売買タイミング判定 → 通知 |
| **PIT ファンダメンタル・スナップショット収集**（🆕 P29） | 16:45（大引け後・決着解決の前） | Vault `Tickers/*.md` frontmatter を全ユニバース分 `pit_fundamental_snapshots` へ追記 |
| **PIT センチメント・スナップショット収集**（🆕 P29） | 16:50 | 候補プール + 保有 + ウォッチの keyword センチメントを `pit_sentiment_snapshots` へ。`llm` はピック生成時に副産物として記録済み |
| 決着解決 | 夜間 | horizon 到来分を解決 |
| 評価指標更新 | 決着後 | `eval_snapshots` / `calibration_curves` |
| 軽量再学習 | 夜間日次 | per-ticker ローテーション（Market Lens 踏襲） |
| PSI ドリフト評価 | 夜間日次 | `drift_snapshots`、必要なら追加再学習 |
| フル再学習 + challenger 構築 + 昇格ゲート | 週次 | `model_promotions` へ提案 |
| **ソース ablation 評価**（🆕 P29） | 四半期（週次フル再学習に相乗り） | 各ソース除外時のホールドアウト指標差分を `source_ablations` へ |
| EOD レビュー | 16:31 前後 | learned heuristics |
| 週次学習差分サマリ | 週次 | `/api/eval/weekly-learning` の材料 |

手動での `.delay()` 投入はしない（Market Lens と同じく quota 無駄打ち防止）。

### 3.7 PIT 特徴量の ML 統合（🆕 P29）

#### 3.7.1 現状のギャップ

`services/learning/feature_engineering.py` の `build_feature_matrix`（断面プール用）・`build_sequence_matrix`（銘柄別 LSTM/Transformer 用）は **どちらも OHLCV 由来のテクニカル指標のみ**（ラグリターン、SMA/EMA/MACD/RSI/ボリンジャー、日付の周期エンコーディング）。`panel_feature_service.build_panel` もその出力 + 断面統計（`xs_rank` / `xs_z` / `sector_rel` / `ticker_te`）+ `dollar_volume` だけで、ファンダメンタル列もセンチメント列も存在しない。

つまり「4 分析（technical / trend / fundamental / sentiment）+ ML」という合成設計のうち、**ML ファクター自体は fundamental / sentiment を一切見ていない**。Vault 由来の情報は `scoring/fundamental_analyzer.get_fundamental_with_vault_fallback` 経由で recommender のヒューリスティック・サブスコアに入るだけで、学習されていない。P29 はこのギャップを塞ぐ。

#### 3.7.2 PIT ファンダメンタル・プロバイダ抽象

データソース非依存の取得層を `services/learning/pit_provider.py`（🆕）に置き、日次収集タスクはこの Protocol にだけ依存する。

```
class PitFundamentalProvider(Protocol):
    source_id: str                      # "vault_frontmatter" / "shikiho" / "jquants" …
    async def fetch(code) -> PitFundamentalRecord | None   # 数値・enum のみ。生テキストは返さない
```

- 第 1 実装は `VaultFrontmatterProvider`（`brand_notes_service.get_brand_note` の `BrandNote` を写すだけ）。
- 四季報は `SHIKIHO_ENABLED=true` になった時点で `ShikihoProvider` を**追加**するだけで済む（`source` 列と `extra` JSON があるため、スキーマ変更もモデル再設計も不要）。既存行の `source='vault_frontmatter'` はそのまま残り、時系列の連続性は `source` 列で識別できる。
- 失敗は `None` を返すフェイルソフト（`data/training_data_source.py` の yfinance→J-Quants フォールバックと同じ設計パターン）。1 銘柄の失敗で当日のスナップショット全体を落とさない。

#### 3.7.3 断面パネルへの結合（lookahead 禁止）

`services/learning/pit_feature_service.py`（🆕）が `load_pit_features(dates, codes) -> DataFrame`（キー `date` / `code`）を返し、`panel_feature_service.build_panel` が **left join** する。

- **as-of backward join のみ**: ある学習行 `(as_of, code)` に結合してよいのは `snapshot_date <= as_of` の最新行だけ。乖離が `PIT_ASOF_TOLERANCE_BDAYS`（既定 5 営業日）を超えたら NaN 扱い（古すぎる値を引きずらない）。
- **`Tickers/*.md` の現在値を過去行へ broadcast する実装は禁止**。この不変条件は単体テストで固定する（「`snapshot_date > as_of` の行が結合対象に混入したら fail」）。
- **欠損は NaN のまま**渡す（XGBoost は欠損を分岐としてネイティブに扱う）。0 埋めはしない — 「PER が 0」と「PER 不明」は別の意味。
- **`has_pit_fundamental` / `has_pit_sentiment_keyword` / `has_pit_sentiment_llm` の 0/1 フラグ列を必ず付ける**。欠損そのものが情報を持つうえ、ブートストラップ期間中に全行 0 になっても列が消えず `model_registry.feature_list` が安定する。
- **断面化**: 絶対水準（PER 15 倍）より「その日のユニバース内・同セクター内での相対位置」のほうが意味を持つため、`add_cross_sectional_features` の `_DEFAULT_RANK_COLS` へ `per_forecast` / `pbr` / `roe` / `dividend_yield_forecast` を、`_DEFAULT_SECTOR_REL_COLS` へ `roe` を追加する。
- **派生列**: `data_staleness_days`（= `snapshot_date - data_as_of`）、`days_since_earnings`。どちらも PIT 台帳の中だけで計算でき、未来を参照しない。

#### 3.7.4 ブートストラップ（貯まるまでの扱い）

PIT 台帳は実装日から前向きにしか貯まらない。学習投入は被覆率ゲートで自動判定する。

```
for group in (pit_fundamental, pit_sentiment_keyword, pit_sentiment_llm):
    covered_days  = パネルの as_of 日のうち、その group の行が存在する日数
    covered_ratio = パネル全行のうち、その group が非欠損の行の割合
    if covered_days < PIT_MIN_COVERAGE_DAYS(既定 120) or covered_ratio < PIT_MIN_COVERAGE_RATIO(既定 0.7):
        その group の列をすべて落として学習する（has_* フラグも落とす）
    判定結果は model_registry.val_metrics の "pit_coverage" へ必ず記録する
```

🔧 2026-09-18: 閾値は当初案（60 営業日 / 50%）ではなく、ユーザー確認のうえ**より厳格な
120 営業日 / 70% で確定**した（`plans/05_決定ログ` §2e #14）。最初の PIT 入り challenger 学習を
安定したデータで行うことを優先する判断。

薄い列を無理に食わせると、XGBoost が「欠損 = 古い期間」という時間軸そのものを学習してしまい（欠損パターンとラベル分布の疑似相関）、ウォークフォワード評価が楽観側へ壊れる。ゲートはそれを防ぐためのもの。全体の投入可否は env `PIT_FEATURES_ENABLED`（既定 `false`）でも上書きできる。

#### 3.7.5 銘柄別モデル（LSTM/Transformer）への扱い

`build_sequence_matrix` は 1 銘柄の時系列ウィンドウであり、シーケンス内でほぼ動かないファンダメンタル水準を全タイムステップに複製しても情報は増えない（パラメータだけ増える）。

- **P29 のスコープは断面プールモデル（`pool_training_service`）のみ**とする。
- 🔧 2026-09-18: 銘柄別モデルへの投入方針をユーザー確認のうえ確定した（`plans/05_決定ログ`
  §2e #16）。当初案（変化量限定・1 年分貯まってから）ではなく、**静的スカラー（PER/PBR/ROE 等の
  生値）も含めて早期・実験的に試す方針**とする。1 年分の蓄積を待たず、`PIT_MIN_COVERAGE_DAYS`
  （120 営業日）を満たした時点で `build_sequence_matrix` への組み込みを別フェーズとして着手する。
  パラメータ増加に対する過学習は challenger 評価（held-out AUC/Brier）で監視し、悪化する場合は
  変化量（`per_change_20d` / `roe_change_60d` / `days_since_earnings`）限定へ切り替える。

#### 3.7.6 既存機構との整合

- **昇格ゲート（§3.3）**: PIT 特徴量入りのモデルは既存 `lane="ml_pool"` の challenger として学習する。**新レーンは作らない**。ホールドアウトは `_purged_date_split` の日付単位パージをそのまま使い、昇格は従来どおり**提案のみ**（`MODEL_AUTO_PROMOTE=false`、`model_promotions` へ記録し API 承認でのみ差し替え）。特徴量が増えたことを理由にゲートを緩めない。
- **ドリフト検知（§3.4）**: §1.9 の `feature_snapshot` 拡張により `pit_fundamental.*` / `pit_sentiment.*` を `drift.MONITORED_FEATURES` へ追加できる。Vault スクレイピングの仕様変更・欠損増加が PSI として可視化される（ドリフト検知が同時に**データ品質監視**として働く）。
- **`source_ablations`（§1.3）**: テーブルは `0001_baseline` に定義済みだが**書き込む実装が存在しない**。P29 で `services/ledger/ablation_service.py`（🆕）を初実装し、四半期ごとに `excluded_source ∈ {pit_fundamental, pit_sentiment, technical, trend}` で列を落として再学習したホールドアウト指標差分を記録する。「Vault を足して本当に良くなったか」の唯一の客観的判定材料になる。
- **プロンプトインジェクション防御**: PIT 台帳に入るのは数値・enum のみ（§1.8）。本経路は **ML 特徴量専用**であり、`services/picks/*_prompt` へ新しい注入経路を一切増やさない。LLM プロンプトへ載るものは従来どおり frontmatter と `render_news_sentiment_block` の enum/number ブロックだけ。
- **教師信号**: ラベルは従来どおり `pool_labeling.cross_sectional_label`（自分の実測前方リターン）。外部由来テキストを教師信号にしない原則（CLAUDE.md）は変わらない — 今回増えるのは**入力特徴量**だけである。

#### 3.7.7 収集スコープとコスト
